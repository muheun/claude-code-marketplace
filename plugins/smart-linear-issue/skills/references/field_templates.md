# 필드 템플릿 및 기본값

Linear 이슈 필드 설정 가이드입니다.

## 우선순위 (Priority)

Linear 우선순위 값과 사용 기준:

| 값 | 레벨 | 이모지 | 사용 기준 |
|---|------|--------|----------|
| 0 | No priority | ⚪ | 우선순위 미지정 (기본값) |
| 1 | Urgent | 🔴 | 프로덕션 장애, 데이터 손실 위험 |
| 2 | High | 🟠 | 핵심 기능 버그, 릴리스 블로커 |
| 3 | Normal | 🟡 | 일반 기능, 개선 사항 |
| 4 | Low | 🟢 | 사소한 개선, 기술 부채 |

### 우선순위 선택 가이드

**🔴 Urgent (1)**
- 프로덕션 서비스 중단
- 보안 취약점 발견
- 데이터 손실/손상 위험
- 규정 준수 위반

**🟠 High (2)**
- 핵심 비즈니스 기능 버그
- 다음 릴리스 필수 항목
- 많은 사용자에게 영향
- 외부 마감 기한 있음

**🟡 Normal (3)** - 기본값
- 일반적인 기능 추가
- 일반적인 버그 수정
- 사용자 경험 개선

**🟢 Low (4)**
- 기술 부채 해결
- 문서 업데이트
- 사소한 UI 개선
- "있으면 좋은" 기능

## 예상 소요 (Estimate)

### 팀 설정 현황

현재 팀의 Linear 추정 설정:

| 설정 | 값 | 설명 |
|------|-----|------|
| Issue estimation | **T-Shirt** | -, XS, S, M, L, XL 사이즈 사용 |
| Allow zero estimates | ✅ ON | 0 포인트 추정 허용 |
| Extended estimate scale | ❌ OFF | 기본 스케일만 사용 |
| Count unestimated issues | ✅ ON | 미추정 이슈 = 1 포인트로 계산 |

### T-Shirt 사이즈 기준 (팀 설정)

| 사이즈 | 값 | 예상 소요 | 복잡도 | 예시 |
|--------|-----|----------|--------|------|
| - | 0 | 해당 없음 | 추정 불필요 | 부모 이슈, 추적용 이슈 |
| XS | 1 | 1-2시간 | 매우 단순 | 텍스트 수정, 간단한 버그 |
| S | 2 | 반나절~1일 | 단순 | 작은 기능, API 수정 |
| M | 3 | 2-3일 | 보통 | 일반 기능 구현 |
| L | 5 | 3-5일 | 복잡 | 여러 컴포넌트 수정 |
| XL | 8 | 1주일 | 매우 복잡 | 대규모 기능, 아키텍처 변경 |

### 추정 선택 가이드

**- (0 포인트)**: 추정 불필요한 경우
- 부모/에픽 이슈 (하위 이슈로 추정)
- 추적용 이슈, 메타 이슈

**XS (1)**: 즉시 처리 가능
- 오타 수정, 설정 변경
- 간단한 CSS 조정
- 로그 메시지 수정

**S (2)**: 반나절 작업
- 단일 함수 추가/수정
- API 엔드포인트 1개
- 간단한 UI 컴포넌트

**M (3)**: 일반적인 작업 - 기본값
- 새 기능 구현
- 버그 조사 및 수정
- 테스트 코드 작성

**L (5)**: 신중한 계획 필요
- 여러 파일 수정
- 복잡한 비즈니스 로직
- 외부 API 연동

**XL (8)**: 분할 고려
- 대규모 리팩토링
- 새 시스템 구축
- 아키텍처 변경

### 추정 팁

- **불확실하면 한 단계 높게**: S vs M 고민되면 M 선택
- **XL 초과 예상되면 분할**: 하위 이슈로 분리 권장
- **미추정 시 1 포인트**: 팀 설정에 따라 미추정 이슈는 1 포인트로 계산됨

### 포인트 기반 참고 (다른 팀 참조용)

| 포인트 | 예상 소요 시간 | 복잡도 | 예시 |
|--------|-------|--------|------|
| 1 | 1-2시간 | 매우 단순 | 텍스트 수정, 간단한 버그 |
| 2 | 1일 | 단순 | 작은 기능, API 수정 |
| 3 | 2-3일 | 보통 | 일반 기능 구현 |
| 5 | 3-5일 | 복잡 | 여러 컴포넌트 수정 |
| 8 | 1주일 | 매우 복잡 | 대규모 기능, 아키텍처 변경 |
| 13 | 2주 이상 | 분할 권장 | 에픽 수준, 이슈 분리 필요 |

## 라벨 가이드

### 일반 라벨 구조

**타입 라벨:**
- `Bug` - 버그/오류
- `Feature` - 새 기능
- `Improvement` - 개선
- `Documentation` - 문서

**영역 라벨:**
- `Frontend` - 프론트엔드
- `Backend` - 백엔드
- `Database` - 데이터베이스
- `Infrastructure` - 인프라

**상태 라벨:**
- `Blocked` - 차단됨
- `Needs Review` - 리뷰 필요
- `Ready` - 작업 가능

### 라벨 선택 팁

- 타입 라벨 1개 + 영역 라벨 1-2개 권장
- 상태 라벨은 필요할 때만
- 팀 규칙이 있으면 팀 규칙 따르기
