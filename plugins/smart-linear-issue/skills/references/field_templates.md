# 필드 템플릿 및 기본값

Linear 이슈 필드 설정 가이드입니다.

## 우선순위 (Priority)

Linear 우선순위 값과 사용 기준:

| 값 | 레벨 | 이모지 | 사용 기준 |
|---|------|--------|----------|
| 0 | No priority | ⚪ | 우선순위 미지정 (기본값) |
| 1 | Urgent | 🔴 | 프로덕션 장애, 데이터 손실 위험 |
| 2 | High | 🟠 | 핵심 기능 버그, 릴리스 블로커 |
| 3 | Normal | 🟡 | 일반 기능, 개선 사항 |
| 4 | Low | 🟢 | 사소한 개선, 기술 부채 |

### 우선순위 선택 가이드

**🔴 Urgent (1)**
- 프로덕션 서비스 중단
- 보안 취약점 발견
- 데이터 손실/손상 위험
- 규정 준수 위반

**🟠 High (2)**
- 핵심 비즈니스 기능 버그
- 다음 릴리스 필수 항목
- 많은 사용자에게 영향
- 외부 마감 기한 있음

**🟡 Normal (3)** - 기본값
- 일반적인 기능 추가
- 일반적인 버그 수정
- 사용자 경험 개선

**🟢 Low (4)**
- 기술 부채 해결
- 문서 업데이트
- 사소한 UI 개선
- "있으면 좋은" 기능

## 예상 소요 (Estimate)

포인트 기반 예상 소요 기준:

| 포인트 | 예상 소요 시간 | 복잡도 | 예시 |
|--------|---------------|--------|------|
| 1 | 1-2시간 | 매우 단순 | 텍스트 수정, 간단한 버그 |
| 2 | 반나절 | 단순 | 작은 기능, API 수정 |
| 3 | 1일 | 보통 | 일반 기능 구현 |
| 5 | 2-3일 | 복잡 | 여러 컴포넌트 수정 |
| 8 | 1주일 | 매우 복잡 | 대규모 기능, 아키텍처 변경 |
| 13 | 2주 이상 | 분할 권장 | 에픽 수준, 이슈 분리 필요 |

### 예상 소요 팁

- **불확실하면 높게**: 2 vs 3 고민되면 3 선택
- **13 이상이면 분할**: 하위 이슈로 분리
- **팀 기준 따르기**: 팀마다 포인트 의미 다름

## 라벨 가이드

### 일반 라벨 구조

**타입 라벨:**
- `Bug` - 버그/오류
- `Feature` - 새 기능
- `Improvement` - 개선
- `Documentation` - 문서

**영역 라벨:**
- `Frontend` - 프론트엔드
- `Backend` - 백엔드
- `Database` - 데이터베이스
- `Infrastructure` - 인프라

**상태 라벨:**
- `Blocked` - 차단됨
- `Needs Review` - 리뷰 필요
- `Ready` - 작업 가능

### 라벨 선택 팁

- 타입 라벨 1개 + 영역 라벨 1-2개 권장
- 상태 라벨은 필요할 때만
- 팀 규칙이 있으면 팀 규칙 따르기
