## Core Principle

Domain modules own the meaning of an error or event. The application or outbound presentation boundary chooses a locale and renders user-facing text.

Do not make reusable `api/core` logic depend on Spring internationalization, an HTTP request, or a translated sentence. Translation is presentation behavior even when the semantic error originates in a domain service.

## Responsibility Quick Reference

| Responsibility | Default owner |
|---|---|
| Error/event meaning and triggering rule | Owning domain `api/core` |
| Stable domain error code and safe formatting arguments | Owning domain `api` when it crosses the public service contract |
| HTTP status and public response-code mapping | `app` or `shared:web-support` |
| `Accept-Language`, supported locales, default and fallback | Executable `app` |
| HTTP representation language and cache variation | Executable `app` |
| `MessageSource` lookup and response rendering | `app` or an intentionally shared `shared:web-support` implementation |
| Business translation bundles | Executable `app` by default |
| Recipient locale and Slack/email/push rendering | App workflow by default; outbound adapter only for provider-owned locale data |
| Logs, configuration failures, DB and invariant diagnostics | Originating module; not localized for users |

## Classify Messages Before Moving Them

- **Client-visible errors:** carry a stable semantic code and arguments across the service boundary; render at the HTTP boundary.
- **Notifications, email, chat, and push content:** carry semantic event data to an outbound rendering boundary; render for the explicit recipient locale and channel.
- **Internal diagnostics:** keep a stable developer-facing message, usually English, and never expose the raw exception text through a 5xx response.
- **Request validation:** app-owned request DTO validation may use message keys; domain validation stays web-neutral and reports semantic errors.

Do not translate every string literal mechanically. A startup failure such as an invalid JWT secret, a persistence invariant, or an operator-facing log message is not a localized client contract.

## Domain Error Contract

When an error can cross a reusable service boundary:

- Define a typed domain exception or result carrying a stable error code and safe arguments.
- Keep Spring `MessageSource`, `LocaleContextHolder`, servlet types, HTTP status codes, and translated text out of `api/core`.
- Do not pass `Locale` through ordinary service methods solely to format exceptions.
- Keep message keys in the app mapping by default. A domain code may expose a message key only when multiple host applications intentionally share the same wording contract.
- Treat a public client `code` and an internal message-bundle key as different contracts. Add a response `code` only when the API explicitly adopts stable client error codes; do not expose a bundle key accidentally.
- Never put secrets, credentials, raw provider responses, or sensitive personal data in formatting arguments.

`IllegalArgumentException("translated sentence")` is not a scalable service contract. It loses semantic identity, makes tests depend on one language, and tempts controllers to expose arbitrary exception text.

## HTTP Locale Policy

The HTTP and Spring Security sections in this reference target Servlet-stack Spring MVC. For WebFlux, keep the ownership and message-contract principles but use reactive locale, exception, filter, and Security APIs; do not register Servlet `LocaleResolver`, `HandlerInterceptor`, `AuthenticationEntryPoint`, or `AccessDeniedHandler` implementations in a reactive application.

Define the following explicitly for every localized API:

- supported language tags;
- default locale;
- missing-header and blank-header behavior;
- unsupported-language fallback;
- region-tag behavior such as `en-US` and `ko-KR`;
- whether query parameters, cookies, or user preferences may override `Accept-Language`, and whether each override must also affect Security filter-chain failures;
- whether localized responses are cacheable and which locale inputs vary the representation.

For an HTTP API, prefer `Accept-Language` with an `AcceptHeaderLocaleResolver`. Do not depend on the JVM or host operating-system locale. Configure a deterministic default. For example, a Korean-first application may support Korean and English and fall back to Korean:

```java
@Bean(name = DispatcherServlet.LOCALE_RESOLVER_BEAN_NAME)
LocaleResolver localeResolver() {
    AcceptHeaderLocaleResolver resolver = new AcceptHeaderLocaleResolver();
    resolver.setSupportedLocales(List.of(Locale.KOREAN, Locale.ENGLISH));
    resolver.setDefaultLocale(Locale.KOREAN);
    return resolver;
}
```

Expose every application-selected resolver, including a custom composite resolver, under the reserved bean name `localeResolver`, preferably with `@Bean(name = DispatcherServlet.LOCALE_RESOLVER_BEAN_NAME)` or a `localeResolver` bean method. `DispatcherServlet` selects this strategy by name, and Spring Boot's default resolver also backs off by name. A differently named custom resolver can coexist with the default and make MVC and Security use different policies. Verify the selected resolver through the real application context and an MVC request, not only by injecting the custom implementation.

Do not combine `AcceptHeaderLocaleResolver` with `LocaleChangeInterceptor`. The interceptor changes locale through `LocaleResolver.setLocale(...)`, while `AcceptHeaderLocaleResolver` deliberately does not support that operation and throws `UnsupportedOperationException`.

For a persistent query override, choose the resolver from the application's state model. `CookieLocaleResolver` can persist a client-held preference without creating server session state. Use `SessionLocaleResolver` only when the application already requires `HttpSession` and the Security session policy is intentionally stateful; never create a session only to remember locale in a stateless JWT/API application. Do not rely on either resolver or `LocaleChangeInterceptor` to enforce the application's supported locales. Parse and match the selector against the explicit allowlist before storing it in a cookie or session. Treat malformed, repeated, stale, or unsupported values as ineligible and continue to the next selector without changing persisted state. If the product requires a 4xx for an invalid locale change, expose a dedicated locale-change endpoint; an invalid selector on a request whose primary contract is a Security 401/403 must not replace that response. Configure or wrap cookie parsing so malformed cookie content falls back safely instead of turning a Security response into a 500.

Treat Java's `Locale.forLanguageTag(...)` as a lenient conversion API, not an input validator. It discards the first ill-formed subtag and everything after it, so code that allowlists only `getLanguage()` can accidentally accept values such as `ko-%%%%`, `ko--KR`, or `ko-x` as Korean. After enforcing the selector's declared blank, multiplicity, and size limits, validate the entire tag with `new Locale.Builder().setLanguageTag(value).build()` and treat `IllformedLocaleException` as ineligible. Only then apply the application's supported-locale allowlist and its explicit region matching or fallback rule. `Locale.Builder` checks syntax, not IANA registration or application support, so the allowlist remains mandatory.

For a request-only override or a precedence chain that mixes query, header, and trusted user preference, prefer one app-owned, side-effect-free policy that accepts only selectors eligible for the current trust state. MVC resolves through the reserved `localeResolver` bean, while each Security handler calls the same policy directly.

If a filter precomputes request-visible selectors, choose exactly one placement contract:

- **Container-level selector filter:** Use this only when a request-visible selector must be computed for all Servlet requests. Register it once with a `FilterRegistrationBean` at an order earlier than the container's `DelegatingFilterProxy` for `springSecurityFilterChain`. This code runs before Spring Security's `FilterChainProxy` and `HttpFirewall`, so keep it side-effect-free and limit it to bounded parsing of allowlisted request-visible values. Do not create or modify a session, write a locale cookie, call a preference store, or make authentication or authorization decisions there.
- **Security-chain selector filter:** Use this when only selected `SecurityFilterChain` instances need the precomputation. Add it to every affected chain with `HttpSecurity#addFilterBefore(...)`, anchored before the earliest authentication or authorization filter that can produce a localized failure on that chain. This filter is inside `springSecurityFilterChain`, not before it, but it still only computes request state and does not persist the selector. If a Spring `Filter` bean is added this way, disable its Servlet-container auto-registration, for example with a disabled `FilterRegistrationBean`, so it does not execute twice.

Do not register the same filter through both contracts. Being merely before `DispatcherServlet` is insufficient because Security can terminate the request first. Keep both selector-filter placements side-effect-free. `StrictHttpFirewall` can defer header or parameter validation until the wrapped request is accessed, so merely entering a `SecurityFilterChain` does not prove that no later firewall rejection can occur. Persist a valid selector only at the final accepted response boundary: after that path has completed every required access to the firewalled request and before the response commits, or in a dedicated locale-change endpoint. When downstream completion occurs after the response has committed, integrate persistence into the final MVC/Security renderer instead of an early filter or `preHandle` interceptor. Do not load a server-stored preference before authentication: supply it only after successful authentication, such as from the trusted principal in an authenticated 403 or later MVC processing. If either placement binds `LocaleContextHolder`, restore the previous context in `finally` and verify error and async dispatch behavior. Real filter-chain tests must show that the filter runs once and that its selected value is visible before the earliest failure-producing filter in every affected chain.

Test the framework's actual matching for language-only tags, regional tags, multiple weighted values, and unsupported languages. For persistent or composite policies, also test malformed, repeated, stale, and unsupported query/cookie/session values, prove they are not stored, and verify the configured fallback without relying on the host locale. Include valid-prefix malformed regressions such as `ko-%%%%`, `ko--KR`, and `ko-x`; each must remain ineligible rather than being truncated to `ko`, must not change persisted state, and must not replace an expected 401/403. A stateless application test must prove locale selection does not create an `HttpSession`; when a container-level filter is used, a request rejected by `HttpFirewall` must not write a cookie, create a session, or call a preference store. If the configured firewall restricts headers or parameters lazily, exercise a rejection raised when the wrapped request is accessed and prove an earlier selector filter did not persist state. Add a custom resolver only when the required policy cannot be expressed by the standard resolver.

Do not assume a blank `Accept-Language` header behaves like a missing header on every supported Spring version. Resolver behavior changed even between Spring Framework patch releases: versions that check only for a missing header can let a blank value fall through to the servlet container locale, while newer versions also treat blank as missing. Verify the exact deployed version and, when both cases must fall back identically, use a small app-owned resolver that normalizes a blank value before delegating. Tests must prove that neither case falls through to the servlet container or JVM locale.

For a localized HTTP representation, set `Content-Language` from the final selected locale rather than echoing the raw request tag. Account for locale in every relevant cache: merge `Accept-Language` into the existing `Vary` header for header negotiation, keep a query selector in the target URI and ensure configured caches do not discard it, and include the effective locale in server-side application cache keys. Use `Vary: Cookie` only when intentionally accepting its broad variation. A server-side preference that is not represented in the request cannot participate in `Vary`, so `private` alone is insufficient. Use `private, no-cache` with a representation-specific validator when the origin can reselect the current preference and validate every reuse; use `no-store` when storage is forbidden or correct revalidation cannot be guaranteed.

Cache keys select a variant; validators describe the selected representation. When using `ETag`, derive it from the rendered representation or combine the resource revision with the effective locale and translation/template revision. Do not reuse a domain entity version as the same validator for every language variant. Any `Last-Modified` value used for conditional requests must reflect changes to both the resource and the selected translation/template; when that cannot be guaranteed, omit that validator or prefer a representation-derived `ETag`. Use `no-store` only when the response itself cannot be cached safely. Test that changing locale or translation content cannot produce a false `304 Not Modified`. Treat these as application HTTP and caching decisions, not domain concerns.

## Message Bundles and Keys

- Put the default language in the base bundle, such as `messages.properties`, and add one bundle per additional language, such as `messages_en.properties`.
- When the base bundle is Korean, `messages_ko.properties` is unnecessary unless a distinct Korean override is intentional.
- Disable system-locale fallback so the host JVM cannot select a language-specific bundle ahead of the Korean base bundle. With Spring Boot auto-configuration, set `spring.messages.fallback-to-system-locale: false`; with a directly configured `AbstractResourceBasedMessageSource`, set the equivalent `fallbackToSystemLocale` option to `false`.
- When declaring the application-wide `ResourceBundleMessageSource` or `ReloadableResourceBundleMessageSource` directly, expose it under the reserved bean name `messageSource`, preferably with `@Bean(name = AbstractApplicationContext.MESSAGE_SOURCE_BEAN_NAME)` or a `messageSource` bean method. Otherwise the `ApplicationContext` may not adopt it and Spring Boot auto-configuration may create a different source because it backs off by bean name. Set `setDefaultEncoding("UTF-8")` for `.properties` bundles and always verify a representative non-ASCII message through `ApplicationContext.getMessage(...)`, not only by injecting the custom bean. Test MVC adoption only when localized MVC behavior exists, the real `Validator` only when localized Bean Validation exists, and a channel renderer only when outbound localization exists. Do not assume `spring.messages.*` configures a custom bean.
- Use namespaced semantic keys such as `auth.authentication.failed` or `identity.account.inactive`; do not encode the current sentence in the key.
- For application `MessageSource` bundles, require every client-visible key in the base bundle and in each language bundle advertised as a complete translation. A regional bundle such as `messages_en_GB.properties` may intentionally override only selected parent keys; require its keys to exist in the parent/base contract and verify every configured locale through the real `MessageSource` so inherited keys still resolve.
- For public keys passed to `MessageSource.getMessage(..., arguments, locale)`, resolve and format every effective locale with representative safe arguments. Validate `MessageFormat` syntax, argument indexes and types, and unresolved placeholders without asserting exact prose. Choose one `alwaysUseMessageFormat` policy: use `spring.messages.always-use-message-format` for Spring Boot's auto-configured source, but call `setAlwaysUseMessageFormat(...)` on a directly configured `AbstractMessageSource`. The direct source defaults to `false`, so test messages both with and without arguments to protect quote and apostrophe behavior.
- Do not apply `MessageFormat` checks to every placeholder-like syntax. Bean Validation tokens such as `{min}` belong to its interpolation engine and must be exercised through the real `Validator` or MVC path; Slack, email, and other channel templates must be exercised through their renderer.
- Unsupported locales fall back to the configured default. A missing key is a deployment defect: do not return the raw key or a `NoSuchMessageException` body to clients. Log it and use the project's safe generic response while tests fail the incomplete bundle.
- Keep business bundles in the executable app by default so each host can choose wording. If multiple applications prove that a shared bundle is required, place it under a unique basename in a dedicated presentation/resource-support module selected by the executable app, never in domain `api/core`. Avoid duplicate keys across basenames. If an app intentionally overrides a shared key, register the app basename before the shared basename because earlier basenames take precedence, then protect that order with an integration test. Do not introduce shared bundles for a hypothetical future consumer.
- Treat packaged classpath bundles as immutable deployment artifacts and refresh them by redeploying. Use a non-classpath `ReloadableResourceBundleMessageSource` with an explicit refresh interval only when runtime translation updates are a real requirement, then test refresh and failure behavior.

For a Korean-default application that uses Spring Boot's auto-configured `MessageSource`, the essential setting is:

```yaml
spring:
  messages:
    fallback-to-system-locale: false
```

## Centralized HTTP Error Rendering

Use one app-owned exception mapping policy:

1. Convert the typed domain/app exception to HTTP status, optional public code, internal message key, and safe arguments.
2. Resolve the request locale.
3. Resolve the message through `MessageSource`.
4. Return the established error envelope.
5. Map unexpected failures to a generic localized 500 response without exposing the exception message.

Example domain contract:

```java
public enum IdentityErrorCode {
    ACCOUNT_INACTIVE
}

public final class IdentityException extends RuntimeException {
    private final IdentityErrorCode code;
    private final Object[] arguments;

    public IdentityException(IdentityErrorCode code, Object... arguments) {
        super(code.name());
        this.code = code;
        this.arguments = arguments.clone();
    }

    public IdentityErrorCode code() {
        return code;
    }

    public Object[] arguments() {
        return arguments.clone();
    }
}
```

The app maps `ACCOUNT_INACTIVE` to its HTTP status and `identity.account.inactive`, then resolves the text. `getMessage()` remains a stable, non-localized diagnostic for logs; it is not the client response contract. Core tests assert the code and arguments; app tests assert the localized HTTP response. Do not make the domain exception call `MessageSource` or use its localized `getMessage()` as the API contract.

## Spring Security Boundary

`@RestControllerAdvice` participates in Spring MVC exception resolution inside `DispatcherServlet`, including request-mapping and handler-processing failures such as binding or validation errors. Keep those failures in the MVC exception policy. It does not render failures handled outside `DispatcherServlet`, notably Spring Security filter-chain failures. Apply the shared locale-selection policy at the following Security boundaries. Apply the application's error envelope only to app-owned JSON endpoints; browser and protocol endpoints retain their native response contract:

- `RequestRejectedHandler` when `HttpFirewall` rejects a request before or during filter-chain processing;
- `AuthenticationEntryPoint` when an unauthenticated request starts the configured authentication scheme, whether that sends a 401 challenge or redirects/forwards to login;
- `AccessDeniedHandler` when an authenticated request is denied, normally with 403;
- `AuthenticationFailureHandler` when a form or provider authentication attempt fails;
- custom JWT/security filters that must delegate expected authentication failures to the configured entry point.

`RequestRejectedHandler` is owned by `FilterChainProxy`, so it is one global firewall-rejection policy rather than a per-`SecurityFilterChain` handler. A rejection may occur before chain selection or later when code accesses the firewalled request, so no in-chain locale filter is a reliable prerequisite. Configure the handler through `WebSecurity#requestRejectedHandler(...)`, commonly from a `WebSecurityCustomizer`, rather than `HttpSecurity#exceptionHandling(...)`. Decide its response contract separately: retaining a fixed, non-localized, generic rejection response is the safest default; use a localized app JSON response only when that consistency is an explicit product contract. A localized handler may use only a bounded, allowlisted locale already placed in a request attribute by the side-effect-free container-level selector filter, otherwise it falls back deterministically. It must not parse or echo the rejected URI, parameters, headers, or cookies; persist locale; create a session; query a preference store; identify a user; or expose the `RequestRejectedException` message. Preserve the configured firewall-rejection status, normally 400, and a safe body/media type.

Chain-level Security handlers must call an app-owned request-locale policy directly; do not assume `LocaleContextHolder` has been populated or that any filter ordered only before `DispatcherServlet` has run. The policy may delegate to the configured `LocaleResolver` when all eligible selectors are already represented there, but it must handle malformed selector/cookie values without replacing the Security response. A `LocaleChangeInterceptor` and other MVC `HandlerInterceptor` logic has not run for a Security filter-chain failure. When a query override must affect those failures, either parse it in the handler's shared side-effect-free policy or use exactly one of the container-level or Security-chain filter placements defined in HTTP Locale Policy. If a valid query must also be persisted on an accepted 401/403 or authentication-failure response, the final app-owned handler first completes every required firewalled-request access, chooses its failure contract, and only then writes the cookie before committing the response; an earlier selector filter must not do so. Resolve a server-stored preference only after successful authentication; do not attempt it in either pre-authentication placement. Otherwise, scope the override to MVC responses and document the Security fallback. An app-owned JSON API Security handler may serialize the application's shared response DTO with its JSON mapper; redirect, forward, and protocol-owned handlers retain their native response contract. Do not concatenate a localized string into raw JSON.

Make selector eligibility depend on authentication trust, even when MVC and Security share one precedence policy. Use a server-stored user preference only from a successfully authenticated principal, as in an authenticated 403 flow. For a 401 `AuthenticationEntryPoint` or `AuthenticationFailureHandler`, do not identify an account or query a preference repository/store from a failed JWT subject, presented login identifier, or authentication exception data. Those values are not a trusted principal, and observable lookup or timing differences can enable account enumeration and load amplification. Use only allowlisted request-visible selectors, such as a valid query value, `Accept-Language`, or a safely parsed locale cookie, then fall back to the application default. Real filter-chain tests must prove that 401 and authentication-failure paths do not call the preference store.

Localizing the body must not replace the authentication scheme's protocol contract. Preserve the framework handler's status, scheme-specific `WWW-Authenticate` challenge and parameters, redirect behavior, media type, and protocol-owned structured error body where applicable. Spring Authorization Server token and other OAuth2/OIDC protocol endpoints return standard error fields through framework protocol handlers such as `OAuth2ErrorAuthenticationFailureHandler`; keep or delegate to those handlers instead of wrapping their output in the application's common envelope. Localize a protocol field only when the governing protocol and the application's client contract explicitly allow it. If direct delegation commits or redirects the response, keep that handler for browser flows and select an app-owned JSON handler only for ordinary API endpoints. Protect status, headers, redirect/forward behavior, media type, and body schema with real-filter-chain tests. Do not apply a common JSON envelope indiscriminately to form-login, OAuth2 authorization redirects, or protocol-owned OAuth2/OIDC endpoints.

Keep expected authentication failures distinct from database, infrastructure, and programming errors. Localization must not turn unexpected failures into 401 or expose their messages.

## Non-HTTP and Recipient-Specific Messages

Request locale is the wrong source for batch, scheduled, async, or multi-recipient work.

- Core decides that a semantic event occurred and which recipient or target is involved.
- The app workflow loads the recipient's locale and passes it explicitly to the outbound port/adapter. Let an outbound adapter resolve locale only when that locale is provider-owned data within the external channel contract; it must not reach into another domain's repository.
- A channel-specific renderer receives semantic data, template key, and explicit recipient locale.
- Slack text, email subject/body, and push text may use different keys because channel constraints and wording evolve independently.
- The channel renderer owns context-specific output encoding. `MessageSource` and `MessageFormat` do not make arguments safe for HTML, URLs, Slack markup, or mentions. Encode URL components for their exact position, and validate a complete untrusted URL against the allowed schemes and hosts; escaping alone cannot make `javascript:` or an attacker-controlled host safe. Prefer structured channel APIs over interpolated markup.
- Choose retry semantics explicitly. A latest-preference retry stores semantic event data and re-resolves the recipient locale and current template on each attempt. Deterministic reproduction snapshots the selected locale and template/version with the semantic inputs; when byte-for-byte or audit-exact output is the contract, retain the final channel-safe artifact under the project's sensitive-data retention policy.

Do not read `LocaleContextHolder` from core or a background thread. Do not create a global static message helper that silently chooses the current thread locale.

## backend-util Extraction Gate

Use Spring `MessageSource` directly in one application. Do not add a `MessageUtil` wrapper merely to shorten `getMessage(...)`.

Extract to `backend-util` only after at least two real applications share the same contract and all of these are stable:

- error descriptor shape;
- locale resolution and fallback behavior;
- missing-key policy;
- exception-to-response ownership;
- Spring Boot version and auto-configuration expectations.

An extracted library may provide a DB/web-neutral error descriptor and optional Spring adapter or auto-configuration. It must not own project business keys, translations, supported locales, default locale, HTTP status mapping, or channel templates. Do not change an existing exception's human-readable `getMessage()` into a bundle key without an explicit compatibility migration.

## Verification Matrix

Select only rows exercised by the changed behavior; do not multiply every locale, error, and channel into an indiscriminate Cartesian product.

| Layer | Required behavior |
|---|---|
| Domain service, when it emits a client-visible error/event | Correct error/event code and safe arguments; no locale dependency |
| MVC exception mapping, when HTTP localization exists | Reserved `localeResolver` bean adoption, supported locales, configured selector precedence, resolver/interceptor compatibility, malformed and unsupported persistent selectors, no locale-only session creation in stateless applications, missing and blank headers, `Content-Language`, cache variation for request-visible selectors, mandatory representation-specific revalidation for server-side preferences, or `no-store`, response envelope, safe 5xx |
| Security firewall rejection, when the response policy is customized | One global `RequestRejectedHandler` exercised through the configured `HttpFirewall` and real `FilterChainProxy`; fixed generic fallback or only a safely precomputed allowlisted locale; preserved rejection status and safe media type/body; execution stops at the rejection point, with no selected-chain filter for a pre-selection rejection and no controller afterward; no handler-owned persistence, session creation, preference lookup, raw rejected input, or exception-message exposure; configured lazy header/parameter rejection covered when applicable |
| Security filter chain, for each configured `AuthenticationEntryPoint`, `AccessDeniedHandler`, or `AuthenticationFailureHandler` | Every handler-visible selector and documented fallback, any precomputed-selector filter registered exactly once through the selected placement and observed before the earliest relevant failure-producing filter in every affected chain, selector filters remain side-effect-free and any valid selector persistence occurs only in the final accepted response boundary, malformed-selector safety, selector eligibility for the current authentication trust state, no preference-store call for 401/authentication failure, localized app-owned representation or native browser/protocol flow, scheme-specific status, challenge headers, redirect/forward behavior, protocol media type and structured error body, and safe failure mapping through the real filter chain |
| Bundle and interpolation contract | Base and complete language bundles have all owned keys; partial regional overrides have valid parent keys; the application source uses the reserved `messageSource` bean name and resolves through the real `ApplicationContext`; every configured locale resolves through each actual consumer path; directly configured message sources decode representative non-ASCII text and exercise the selected `setAlwaysUseMessageFormat(...)` behavior with and without arguments |
| Validation, when localized request validation exists | App request validation resolves localized messages; domain validation remains semantic |
| Async/outbound, when recipient messages exist | Different locales render independently, hostile arguments are channel-safe, and retries follow the chosen latest or deterministic contract |

Prefer focused behavior tests over broad source scans for every string literal. A small architecture rule may protect the stable dependency boundary that `api/core` do not depend on Spring context or web support; message wording and key layout remain behavior and review concerns.

## Common Mistakes

- Injecting `MessageSource` or reading `LocaleContextHolder` in `*:core`.
- Passing `Locale` through service methods only to format an exception.
- Treating an internal bundle key as a stable public API code without deciding that contract.
- Localizing logs and startup/infrastructure exceptions while leaving Security responses hard-coded.
- Assuming `@RestControllerAdvice` handles filter-chain failures.
- Pairing `AcceptHeaderLocaleResolver` with `LocaleChangeInterceptor`, which calls the resolver's unsupported `setLocale(...)` operation.
- Registering a custom `LocaleResolver` under a name other than `localeResolver`, so MVC keeps using the default strategy.
- Using `Locale.forLanguageTag(...)` as selector validation and allowlisting only its truncated language result.
- Treating any pre-`DispatcherServlet` filter as early enough for Security, confusing a container filter before `DelegatingFilterProxy` with a filter inside `springSecurityFilterChain`, registering the same filter in both places, mutating session/cookie/store state before `HttpFirewall`, or loading a stored user preference before authentication.
- Assuming controller advice, an entry point, or an in-chain locale filter handles `HttpFirewall` rejection; configuring `RequestRejectedHandler` as if it were per chain; or localizing it from rejected raw request data or exception text.
- Persisting a syntactically valid but unsupported locale, using `SessionLocaleResolver` only to add state to a stateless application, or letting malformed query/cookie values replace the original Security response.
- Configuring the application `MessageSource` under a name other than `messageSource`, omitting explicit `.properties` encoding, or assuming Spring Boot message properties configure the direct bean.
- Looking up a stored user preference from a failed JWT subject or presented login identifier in a 401 or authentication-failure path.
- Building JSON with string concatenation in an authentication handler.
- Replacing a scheme-specific Security handler and losing its `WWW-Authenticate` challenge, redirect behavior, media type, or protocol-owned structured error body.
- Echoing raw `Accept-Language` as `Content-Language`, omitting a request-visible locale selector from a cache key, reusing one `ETag` across different language representations, omitting mandatory revalidation for a server-side preference, or treating `private` alone as sufficient.
- Requiring every regional override bundle to duplicate its parent, or checking keys without resolving parameterized messages.
- Using the request locale for scheduled jobs or recipients with different preferences.
- Treating `MessageSource` output as HTML or Slack-safe without output-context encoding, or treating URL escaping as a substitute for allowed scheme/host validation.
- Claiming deterministic retry from semantic event data without snapshotting locale and template/rendered output as required by the contract.
- Creating a static `MessageUtil` before a second real consumer proves a reusable contract.
- Shipping incomplete complete-language bundles, invalid partial overrides, or relying on the machine default locale.
