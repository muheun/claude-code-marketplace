## Core Principle

Domain modules own the meaning of an error or event. The application or outbound presentation boundary chooses a locale and renders user-facing text.

Do not make reusable `api/core` logic depend on Spring internationalization, an HTTP request, or a translated sentence. Translation is presentation behavior even when the semantic error originates in a domain service.

## Responsibility Quick Reference

| Responsibility | Default owner |
|---|---|
| Error/event meaning and triggering rule | Owning domain `api/core` |
| Stable domain error code and safe formatting arguments | Owning domain `api` when it crosses the public service contract |
| HTTP status and public response-code mapping | `app` or `shared:web-support` |
| `Accept-Language`, supported locales, default and fallback | Executable `app` |
| HTTP representation language and cache variation | Executable `app` |
| `MessageSource` lookup and response rendering | `app` or an intentionally shared `shared:web-support` implementation |
| Business translation bundles | Executable `app` by default |
| Recipient locale and Slack/email/push rendering | App workflow by default; outbound adapter only for provider-owned locale data |
| Logs, configuration failures, DB and invariant diagnostics | Originating module; not localized for users |

## Classify Messages Before Moving Them

- **Client-visible errors:** carry a stable semantic code and arguments across the service boundary; render at the HTTP boundary.
- **Notifications, email, chat, and push content:** carry semantic event data to an outbound rendering boundary; render for the explicit recipient locale and channel.
- **Internal diagnostics:** keep a stable developer-facing message, usually English, and never expose raw exception text through a 5xx response.
- **Request validation:** app-owned request DTO validation may use message keys; domain validation stays web-neutral and reports semantic errors.

Do not translate every string literal mechanically. A startup failure such as an invalid JWT secret, a persistence invariant, or an operator-facing log message is not a localized client contract.

## Domain Error Contract

When an error can cross a reusable service boundary:

- Define a typed domain exception or result carrying a stable error code and safe arguments.
- Keep Spring `MessageSource`, `LocaleContextHolder`, servlet types, HTTP status codes, and translated text out of `api/core`.
- Do not pass `Locale` through ordinary service methods solely to format exceptions.
- Keep message keys in the app mapping by default; a domain code may expose a message key only when multiple host applications intentionally share the same wording contract.
- Treat a public client `code` and an internal message-bundle key as different contracts. Add a response `code` only when the API explicitly adopts stable client error codes; do not expose a bundle key accidentally.
- Never put secrets, credentials, raw provider responses, or sensitive personal data in formatting arguments.

`IllegalArgumentException("translated sentence")` is not a scalable service contract: it loses semantic identity, makes tests depend on one language, and tempts controllers to expose arbitrary exception text.

## HTTP Locale Policy

The HTTP and Spring Security sections target Servlet-stack Spring MVC. For WebFlux, keep the ownership and message-contract principles but use reactive locale, exception, filter, and Security APIs; do not register Servlet `LocaleResolver`, `HandlerInterceptor`, `AuthenticationEntryPoint`, or `AccessDeniedHandler` implementations there.

Define explicitly for every localized API:

- supported language tags;
- default locale;
- missing-header and blank-header behavior;
- unsupported-language fallback;
- region-tag behavior such as `en-US` and `ko-KR`;
- whether query parameters, cookies, or user preferences may override `Accept-Language`, and whether each override must also affect Security filter-chain failures;
- whether localized responses are cacheable and which locale inputs vary the representation.

For an HTTP API, prefer `Accept-Language` with an `AcceptHeaderLocaleResolver`. Do not depend on the JVM or host operating-system locale; configure a deterministic default. For example, a Korean-first application may support Korean and English and fall back to Korean:

```java
@Bean(name = DispatcherServlet.LOCALE_RESOLVER_BEAN_NAME)
LocaleResolver localeResolver() {
    AcceptHeaderLocaleResolver resolver = new AcceptHeaderLocaleResolver();
    resolver.setSupportedLocales(List.of(Locale.KOREAN, Locale.ENGLISH));
    resolver.setDefaultLocale(Locale.KOREAN);
    return resolver;
}
```

Expose the selected resolver, including any custom composite, under the reserved bean name `localeResolver`, as above. `DispatcherServlet` selects the strategy by name and Spring Boot's default resolver backs off by name, so a differently named resolver silently coexists with the default and MVC and Security can end up with different policies. Verify adoption through the real application context and an MVC request, not only by injecting the custom implementation.

Do not combine `AcceptHeaderLocaleResolver` with `LocaleChangeInterceptor`: the interceptor calls `LocaleResolver.setLocale(...)`, which `AcceptHeaderLocaleResolver` deliberately rejects with `UnsupportedOperationException`.

For a persistent query override, choose the resolver from the application's state model:

- `CookieLocaleResolver` persists a client-held preference without server session state.
- Use `SessionLocaleResolver` only when the application already requires `HttpSession` and the Security session policy is intentionally stateful; never create a session only to remember locale in a stateless JWT/API application.
- Do not rely on either resolver or `LocaleChangeInterceptor` to enforce supported locales: match the selector against the explicit allowlist before storing it.
- Treat malformed, repeated, stale, or unsupported values as ineligible; continue to the next selector without changing persisted state.
- If the product requires a 4xx for an invalid locale change, expose a dedicated locale-change endpoint. An invalid selector on a request whose primary contract is a Security 401/403 must not replace that response.
- Configure or wrap cookie parsing so malformed cookie content falls back safely instead of turning a Security response into a 500.

`Locale.forLanguageTag(...)` is a lenient conversion API, not a validator: it drops the first ill-formed subtag and everything after it, so allowlisting only `getLanguage()` can accept malformed values as Korean. After enforcing the selector's blank, multiplicity, and size limits, validate the whole tag with `new Locale.Builder().setLanguageTag(value).build()`, treating `IllformedLocaleException` as ineligible, then apply the supported-locale allowlist and the explicit region matching or fallback rule — `Locale.Builder` checks syntax only, not IANA registration or application support.

The canonical **valid-prefix malformed regressions** are `ko-%%%%`, `ko--KR`, and `ko-x`: each must remain ineligible rather than truncated to `ko`, must not change persisted state, and must not replace an expected 401/403. Other sections and checklists reference this list by name.

For a request-only override or a precedence chain mixing query, header, and trusted user preference, prefer one app-owned, side-effect-free policy that accepts only selectors eligible for the current trust state. MVC resolves through the reserved `localeResolver` bean; each Security handler calls the same policy directly.

If a filter precomputes request-visible selectors, choose exactly one placement contract:

- **Container-level selector filter:** only when a request-visible selector must be computed for all Servlet requests. Register it once with a `FilterRegistrationBean` ordered earlier than the container's `DelegatingFilterProxy` for `springSecurityFilterChain`. It runs before `FilterChainProxy` and `HttpFirewall`, so limit it to bounded parsing of allowlisted request-visible values.
- **Security-chain selector filter:** when only selected `SecurityFilterChain` instances need the precomputation. Add it to every affected chain with `HttpSecurity#addFilterBefore(...)`, anchored before the earliest filter that can produce a localized failure on that chain. If a Spring `Filter` bean is added this way, disable its Servlet-container auto-registration, for example with a disabled `FilterRegistrationBean`, so it does not execute twice.

These placement rules are normative; other sections reference them rather than restating them:

- Never register the same filter through both contracts. Being merely before `DispatcherServlet` is insufficient because Security can terminate the request first.
- Both placements stay side-effect-free: no session creation, no cookie write, no preference-store call, no authentication or authorization decision.
- **Lazy-rejection rule:** `StrictHttpFirewall` can defer header or parameter validation until the wrapped request is accessed, so entering a `SecurityFilterChain` does not prove that no later firewall rejection can occur.
- **Final-boundary persistence rule:** persist a valid selector only at the final accepted response boundary — after that path has completed every required access to the firewalled request and before the response commits — or in a dedicated locale-change endpoint. If downstream completion occurs after the response has committed, integrate persistence into the final MVC/Security renderer, not an early filter or `preHandle` interceptor.
- Server-stored preferences become eligible only after successful authentication; see Spring Security Boundary.
- If either placement binds `LocaleContextHolder`, restore the previous context in `finally`. Tests must prove no locale leaks across ERROR and ASYNC dispatches and that `LocaleContextHolder` is restored after async execution completes.
- Real filter-chain tests must show the filter runs once and its selected value is visible before the earliest failure-producing filter in every affected chain.

Test the framework's actual matching:

- language-only tags, regional tags, multiple weighted values, and unsupported languages;
- for persistent or composite policies: the ineligibility rules above hold — nothing is stored, the configured fallback applies, no case relies on the host locale;
- the valid-prefix malformed regressions defined above;
- a stateless application proves locale selection creates no `HttpSession`;
- with a container-level selector filter, an `HttpFirewall` rejection — including a lazy rejection raised on wrapped-request access — leaves no cookie, session, or preference-store side effect.

Add a custom resolver only when the required policy cannot be expressed by the standard resolver.

Do not assume a blank `Accept-Language` header behaves like a missing header on every supported Spring version; resolver behavior changed even between patch releases, and versions that check only for a missing header can let a blank value fall through to the servlet container locale. When both cases must fall back identically, normalize the blank value in a small app-owned resolver before delegating, and prove neither case falls through to the container or JVM locale.

For a localized HTTP representation, set `Content-Language` from the final selected locale rather than echoing the raw request tag. Caching rules:

- The effective locale must be part of every cache key: merge `Accept-Language` into the existing `Vary` header, keep a query selector in the target URI, and include the locale in server-side application cache keys. Use `Vary: Cookie` only when intentionally accepting its broad variation.
- Never reuse an `ETag` or `Last-Modified` value across language variants. Derive validators from the rendered representation (resource revision plus effective locale plus translation/template revision) and test that changing locale or translation content cannot produce a false `304 Not Modified`.
- A server-side preference not represented in the request cannot participate in `Vary`. Respond with `private, no-cache` plus a representation-specific validator when the origin can reselect the preference and validate every reuse; use `no-store` when storage is forbidden or correct revalidation cannot be guaranteed.

These are application HTTP and caching decisions, not domain concerns.

## Message Bundles and Keys

- Put the default language in the base bundle, such as `messages.properties`, and add one bundle per additional language, such as `messages_en.properties`. When the base bundle is Korean, `messages_ko.properties` is unnecessary unless a distinct Korean override is intentional.
- Disable system-locale fallback so the host JVM cannot select a language-specific bundle ahead of the base bundle: `spring.messages.fallback-to-system-locale: false` with Spring Boot auto-configuration, or `fallbackToSystemLocale=false` on a directly configured `AbstractResourceBasedMessageSource`.
- When declaring the application-wide message source directly, expose it under the reserved bean name `messageSource`, preferably via `@Bean(name = AbstractApplicationContext.MESSAGE_SOURCE_BEAN_NAME)`; otherwise the `ApplicationContext` may not adopt it, and Spring Boot auto-configuration — which backs off by bean name — may create a different source. Set `setDefaultEncoding("UTF-8")` for `.properties` bundles and verify a representative non-ASCII message through `ApplicationContext.getMessage(...)`, not only by injecting the custom bean. Do not assume `spring.messages.*` configures a custom bean. Test MVC adoption, the real `Validator`, or a channel renderer only when that localized consumer exists.
- Use namespaced semantic keys such as `auth.authentication.failed` or `identity.account.inactive`; do not encode the current sentence in the key.
- Require every client-visible key in the base bundle and in each language bundle advertised as a complete translation. A regional bundle such as `messages_en_GB.properties` may intentionally override only selected parent keys; require its keys to exist in the parent/base contract and verify every configured locale through the real `MessageSource` so inherited keys still resolve.
- For public keys passed to `MessageSource.getMessage(..., arguments, locale)`, resolve and format every effective locale with representative safe arguments, validating `MessageFormat` syntax, argument indexes and types, and unresolved placeholders without asserting exact prose. Choose one `alwaysUseMessageFormat` policy — `spring.messages.always-use-message-format` for the auto-configured source, `setAlwaysUseMessageFormat(...)` on a directly configured `AbstractMessageSource` (default `false`) — and test messages with and without arguments to protect quote and apostrophe behavior.
- Do not apply `MessageFormat` checks to every placeholder-like syntax. Bean Validation tokens such as `{min}` belong to its interpolation engine and are exercised through the real `Validator` or MVC path; Slack, email, and other channel templates through their renderer.
- Unsupported locales fall back to the configured default. A missing key is a deployment defect: do not return the raw key or a `NoSuchMessageException` body to clients. Log it and use the project's safe generic response while tests fail the incomplete bundle.
- Keep business bundles in the executable app by default so each host chooses wording. Only when multiple applications prove a shared bundle is required, place it under a unique basename in a dedicated presentation/resource-support module selected by the app, never in domain `api/core`. Avoid duplicate keys across basenames; if an app intentionally overrides a shared key, register the app basename before the shared basename (earlier basenames win) and protect that order with an integration test. Do not introduce shared bundles for a hypothetical future consumer.
- Treat packaged classpath bundles as immutable deployment artifacts refreshed by redeploying. Use a non-classpath `ReloadableResourceBundleMessageSource` with an explicit refresh interval only when runtime translation updates are a real requirement, then test refresh and failure behavior.

For a Korean-default application using Spring Boot's auto-configured `MessageSource`, the essential setting is:

```yaml
spring:
  messages:
    fallback-to-system-locale: false
```

## Centralized HTTP Error Rendering

Use one app-owned exception mapping policy:

1. Convert the typed domain/app exception to HTTP status, optional public code, internal message key, and safe arguments.
2. Resolve the request locale.
3. Resolve the message through `MessageSource`.
4. Return the established error envelope.
5. Map unexpected failures to a generic localized 500 response without exposing the exception message.

Example domain contract:

```java
public enum IdentityErrorCode {
    ACCOUNT_INACTIVE
}

public final class IdentityException extends RuntimeException {
    private final IdentityErrorCode code;
    private final Object[] arguments;

    public IdentityException(IdentityErrorCode code, Object... arguments) {
        super(code.name());
        this.code = code;
        this.arguments = arguments.clone();
    }

    public IdentityErrorCode code() {
        return code;
    }

    public Object[] arguments() {
        return arguments.clone();
    }
}
```

The app maps `ACCOUNT_INACTIVE` to its HTTP status and `identity.account.inactive`, then resolves the text. `getMessage()` remains a stable, non-localized diagnostic for logs; it is not the client response contract. Core tests assert the code and arguments; app tests assert the localized HTTP response. Do not make the domain exception call `MessageSource` or use its localized `getMessage()` as the API contract.

## Spring Security Boundary

`@RestControllerAdvice` participates in Spring MVC exception resolution inside `DispatcherServlet`, including binding and validation failures; keep those in the MVC exception policy. It does not render failures handled outside `DispatcherServlet`, notably Spring Security filter-chain failures. Apply the shared locale-selection policy at these Security boundaries, and the application's error envelope only to app-owned JSON endpoints — browser and protocol endpoints keep their native response contract:

- `RequestRejectedHandler` when `HttpFirewall` rejects a request;
- `AuthenticationEntryPoint` when an unauthenticated request starts the configured authentication scheme, whether a 401 challenge or a redirect/forward to login;
- `AccessDeniedHandler` when an authenticated request is denied, normally with 403;
- `AuthenticationFailureHandler` when a form or provider authentication attempt fails;
- custom JWT/security filters that must delegate expected authentication failures to the configured entry point.

`RequestRejectedHandler` is owned by `FilterChainProxy`: one global firewall-rejection policy, not a per-`SecurityFilterChain` handler. A rejection may occur before chain selection or later under the lazy-rejection rule in HTTP Locale Policy, so no in-chain locale filter is a reliable prerequisite. Configure it through `WebSecurity#requestRejectedHandler(...)` (Spring Security 5.7+; earlier versions expose a `RequestRejectedHandler` bean instead), commonly from a `WebSecurityCustomizer`, not `HttpSecurity#exceptionHandling(...)`. A fixed, non-localized, generic rejection response is the safest default; localize only when that consistency is an explicit product contract, and then use only a bounded, allowlisted locale precomputed into a request attribute by the container-level selector filter, falling back deterministically. The handler must not parse or echo the rejected URI, parameters, headers, or cookies; persist locale; create a session; query a preference store; identify a user; or expose the `RequestRejectedException` message. Preserve the configured rejection status, normally 400, and a safe body/media type.

Chain-level Security handlers call an app-owned request-locale policy directly. Do not assume `LocaleContextHolder` is populated, that a filter ordered only before `DispatcherServlet` has run, or that `LocaleChangeInterceptor` or other MVC interceptor logic ran. The policy may delegate to the configured `LocaleResolver` when all eligible selectors are represented there, but malformed selector/cookie values must not replace the Security response. When a query override must affect these failures, parse it in the handler's shared side-effect-free policy or use exactly one selector-filter placement per HTTP Locale Policy; persisting a valid query on an accepted 401/403 or authentication-failure response follows the final-boundary persistence rule there, executed by the final app-owned handler after it chooses its failure contract — never by an earlier selector filter. Otherwise, scope the override to MVC responses and document the Security fallback. An app-owned JSON API handler may serialize the application's shared response DTO with its JSON mapper; redirect, forward, and protocol-owned handlers keep their native contract. Do not concatenate a localized string into raw JSON.

Make selector eligibility depend on authentication trust even when MVC and Security share one precedence policy. Use a server-stored preference only from a successfully authenticated principal, as in an authenticated 403 flow. In a 401 `AuthenticationEntryPoint` or `AuthenticationFailureHandler`, never identify an account or query a preference repository/store from a failed JWT subject, presented login identifier, or authentication exception data: those are not a trusted principal, and observable lookup or timing differences can enable account enumeration and load amplification. Use only allowlisted request-visible selectors — a valid query value, `Accept-Language`, or a safely parsed locale cookie — then the application default. Real filter-chain tests must prove 401 and authentication-failure paths never call the preference store.

Localizing the body must not replace the authentication scheme's protocol contract: preserve the framework handler's status, scheme-specific `WWW-Authenticate` challenge and parameters, redirect behavior, media type, and protocol-owned structured error body. Spring Authorization Server token and other OAuth2/OIDC protocol endpoints return standard error fields through framework handlers such as `OAuth2ErrorAuthenticationFailureHandler`; keep or delegate to those handlers instead of wrapping their output in the application envelope, and localize a protocol field only when the governing protocol and the client contract explicitly allow it. If direct delegation commits or redirects the response, keep that handler for browser flows and select an app-owned JSON handler only for ordinary API endpoints. Protect status, headers, redirect/forward behavior, media type, and body schema with real-filter-chain tests. Do not apply a common JSON envelope to form-login, OAuth2 authorization redirects, or protocol-owned OAuth2/OIDC endpoints.

Keep expected authentication failures distinct from database, infrastructure, and programming errors. Localization must not turn unexpected failures into 401 or expose their messages.

## Non-HTTP and Recipient-Specific Messages

Request locale is the wrong source for batch, scheduled, async, or multi-recipient work.

- Core decides that a semantic event occurred and which recipient or target is involved.
- The app workflow loads the recipient's locale and passes it explicitly to the outbound port/adapter. Let an outbound adapter resolve locale only when that locale is provider-owned data within the external channel contract; it must not reach into another domain's repository.
- A channel-specific renderer receives semantic data, template key, and explicit recipient locale.
- Slack text, email subject/body, and push text may use different keys because channel constraints and wording evolve independently.
- The channel renderer owns context-specific output encoding. `MessageSource` and `MessageFormat` do not make arguments safe for HTML, URLs, Slack markup, or mentions. Encode URL components for their exact position, and validate a complete untrusted URL against allowed schemes and hosts; escaping alone cannot make `javascript:` or an attacker-controlled host safe. Prefer structured channel APIs over interpolated markup.
- Choose retry semantics explicitly. A latest-preference retry stores semantic event data and re-resolves the recipient locale and current template on each attempt. Deterministic reproduction snapshots the selected locale and template/version with the semantic inputs; when byte-for-byte or audit-exact output is the contract, retain the final channel-safe artifact under the project's sensitive-data retention policy.

Do not read `LocaleContextHolder` from core or a background thread. Do not create a global static message helper that silently chooses the current thread locale.

## backend-util Extraction Gate

Use Spring `MessageSource` directly in one application. Do not add a `MessageUtil` wrapper merely to shorten `getMessage(...)`.

Extract to `backend-util` only after at least two real applications share the same contract and all of these are stable:

- error descriptor shape;
- locale resolution and fallback behavior;
- missing-key policy;
- exception-to-response ownership;
- Spring Boot version and auto-configuration expectations.

An extracted library may provide a DB/web-neutral error descriptor and optional Spring adapter or auto-configuration. It must not own project business keys, translations, supported locales, default locale, HTTP status mapping, or channel templates. Do not change an existing exception's human-readable `getMessage()` into a bundle key without an explicit compatibility migration.

## Verification Matrix

Select only rows exercised by the changed behavior; do not multiply every locale, error, and channel into an indiscriminate Cartesian product.

| Layer | Required behavior |
|---|---|
| Domain service, when it emits a client-visible error/event | Correct error/event code and safe arguments; no locale dependency |
| MVC exception mapping, when HTTP localization exists | Locale policy behaviors per HTTP Locale Policy: resolver adoption, selector precedence, ineligible selectors, session, missing/blank headers, `Content-Language`, caching; plus response envelope and safe 5xx |
| Security firewall rejection, when the response policy is customized | One global `RequestRejectedHandler` through the configured `HttpFirewall` and real `FilterChainProxy`; generic fallback or allowlisted precomputed locale only; preserved rejection status and safe body/media type; no handler-owned side effects or raw-input exposure; lazy-rejection coverage — details in Spring Security Boundary and HTTP Locale Policy |
| Security filter chain, for each configured `AuthenticationEntryPoint`, `AccessDeniedHandler`, or `AuthenticationFailureHandler` | Handler-visible selectors and documented fallback; selector-filter placement, single registration, side-effect freedom, and final-boundary persistence per HTTP Locale Policy; selector eligibility for the authentication trust state; no preference-store call on 401/authentication failure; scheme and protocol contract preserved — details in Spring Security Boundary |
| Bundle and interpolation contract | Key completeness, reserved `messageSource` bean name, resolution through the real `ApplicationContext` for every configured locale and consumer path, non-ASCII decoding, `alwaysUseMessageFormat` behavior with and without arguments — details in Message Bundles and Keys |
| Validation, when localized request validation exists | App request validation resolves localized messages; domain validation remains semantic |
| Async/outbound, when recipient messages exist | Different locales render independently, hostile arguments are channel-safe, and retries follow the chosen latest or deterministic contract |

Prefer focused behavior tests over broad source scans for every string literal. A small architecture rule may protect the stable dependency boundary that `api/core` do not depend on Spring context or web support; message wording and key layout remain behavior and review concerns.

## Common Mistakes

- Pairing `AcceptHeaderLocaleResolver` with `LocaleChangeInterceptor`, which calls the resolver's unsupported `setLocale(...)` operation.
- Registering a custom `LocaleResolver` under a name other than `localeResolver`, so MVC keeps using the default strategy.
- Using `Locale.forLanguageTag(...)` as selector validation and allowlisting only its truncated language result, which accepts the valid-prefix malformed regressions from HTTP Locale Policy.
- Configuring the application `MessageSource` under a name other than `messageSource`, omitting explicit `.properties` encoding, or assuming Spring Boot message properties configure the direct bean.
- Treating any pre-`DispatcherServlet` filter as early enough for Security, or violating the selector-filter placement and final-boundary persistence rules in HTTP Locale Policy.
- Configuring `RequestRejectedHandler` as if it were per chain, or localizing it from rejected raw request data or exception text.
- Looking up a stored user preference from a failed JWT subject or presented login identifier in a 401 or authentication-failure path.
- Replacing a scheme-specific Security handler and losing its `WWW-Authenticate` challenge, redirect behavior, media type, or protocol-owned structured error body.
- Requiring every regional override bundle to duplicate its parent, or checking keys without resolving parameterized messages.
- Treating `MessageSource` output as HTML or Slack-safe without output-context encoding, or treating URL escaping as a substitute for allowed scheme/host validation.
